## 1. Objective

A fresh `eggpool onboard` creates the local administrator and one personal
client token, and it does not also write a server API key that the same
command retires. A browser that opens a protected HTML page before signing
in is shown how to reach `/login`.

## 2. Why this milestone is ready

No hard or interface dependencies. ADR-0002 already requires the first
administrator and the personal token. This milestone aligns the fresh-install
output with that rule.

## 3. Current implementation evidence

`onboard` in `rust/src/runtime.rs` treats a missing database as
`bootstrap_admin = true` and `identity_initialized = false`.
`should_generate_legacy_server_key` returns true in that case, so the
command writes `[server].api_key` and then calls `identity::bootstrap_admin`,
which sets `admin_initialized`. `legacy_server_key_allowed` in
`rust/src/server/middleware.rs` is true only for `legacy_unmigrated`.

The unit test `onboarding_does_not_create_a_legacy_key_after_admin_initialization`
covers a later run, after identity is already initialized. It does not cover
the same-run bootstrap.

Unauthenticated requests that fall through to the session check return JSON
from `unauthorized`. `GET /login` already renders the sign-in document in
`rust/src/server/auth.rs` and is unconditionally public.
`rust/config.example.toml` says the server key generated by onboard still
guards inference.

## 4. Invariants that must not regress

- A fresh database with no server key still refuses to serve until an
  administrator exists.
- `legacy_unmigrated` continues to accept the configured server key.
- After initialization, the server key still does not authenticate, and
  `dashboard.public` still does not expose admin data.
- `/login` stays public. Inference paths stay authenticated.
- Passwords and tokens stay out of argv and out of logs.

## 5. Scope

### In scope

- Same-run onboard key generation.
- Operator text after bootstrap.
- Unauthenticated HTML response for dashboard and account GET pages when
  the access state is `admin_initialized` or `managed`.
- Comments and docs that tell a fresh install to use the retired server key.

### Explicitly out of scope

- Deleting a server key that was already in the file.
- Changing Argon2id, session cookies, or CSRF.
- Personal upstream accounts.
- A new authentication mode.

## 6. Required production changes

When onboard has decided it will bootstrap an administrator in this
invocation, skip server-key generation. The existing
`should_generate_legacy_server_key(false)` behavior for a later run stays.

If a key is already present and this invocation bootstraps, leave the file
bytes unchanged and print that inference uses the one-time personal token,
not that server key. Print the token once through the existing
`print_one_time_secret` path. Print that browser sign-in is `/login` on the
listen address.

For `GET` of a dashboard page or an account page, when the access state is
`admin_initialized` or `managed` and no session cookie is present, return
`303` to `/login` or a `no-store` HTML page that links to `/login`. Use the
existing sign-in document builder rather than a second visual language.
Apply this only to HTML navigation. `POST`, `/v1/*`, and `/api/*` keep the
JSON 401 body. `legacy_unmigrated` is unchanged, including a public
read-only dashboard.

Update the `[server]` comment in `rust/config.example.toml`. Check
`rust/config.local.example.toml`, `README.md`, and `docs/deployment.md` for
the same fresh-install claim and make those sentences name the personal
token after bootstrap.

## 7. Ordered work packages

### Work package A — Same-run key decision

Intent: The fresh database path does not write a key it is about to retire.

Required changes: Split the "not yet initialized" predicate from the
"this run will bootstrap" predicate in `rust/src/runtime.rs`. Generate a
missing key only when this run will leave the database
`legacy_unmigrated`.

Acceptance evidence: A test with no database and no key asserts no
`api_key` write before bootstrap. A test with identity already initialized
still asserts no key write. A test with an existing key asserts the bytes
are unchanged and the rendered guidance does not call that key the
inference credential.

### Work package B — HTML sign-in handoff

Intent: A browser opened to the dashboard after bootstrap can find `/login`.

Required changes: In `rust/src/server/middleware.rs`, before the JSON
unauthorized return, detect the HTML GET case and delegate the body to
`rust/src/server/auth.rs`. Cache-Control is `no-store`.

Acceptance evidence: A managed-state GET of `/` and `/usage` without a
cookie yields the sign-in handoff. A GET of `/v1/models` and
`/api/user-budget` without a credential yields JSON 401. A
`legacy_unmigrated` public dashboard GET still renders the dashboard.

### Work package C — Operator sentences

Intent: The template and the install docs describe the credential onboard
actually leaves in force.

Required changes: Edit the comments and docs named in section 6. Do not
change the listen default or the legacy-key compatibility statement for
databases that are still `legacy_unmigrated`.

Acceptance evidence: `scripts/validate_release_docs.py` passes. A search
of the edited files does not tell a post-bootstrap install to call
inference with the server key from that onboard run.

## 8. Failure, cancellation, restart, contention semantics

Onboard remains a foreground command. If bootstrap fails after config
creation, the command must not have written a new server key in the
bootstrap path. An interrupted password prompt leaves no administrator and
no new server key. The HTML handoff is stateless and does not create a
session. Restart of the server does not change the access state.

## 9. Compatibility and migration

No schema change. Existing `legacy_unmigrated` installs keep their server
key. Existing initialized installs are unaffected apart from the friendlier
unauthenticated HTML response. No config key is removed automatically.

## 13. Acceptance criteria

- A new configuration and a new database, passed through onboard's
  bootstrap path, contain an administrator, one personal token disclosure,
  and no newly written `[server].api_key`.
- The command's stdout names `/login` and does not name the server key as
  the token to export.
- A browser GET of `/` on a managed instance without a cookie can follow
  one link or redirect to `/login`.
- `curl` of `/v1/models` without a key still receives JSON 401.
- A pre-existing legacy database still authenticates with its server key.

## 14. Stop conditions

Stop if fixing the key write would let a keyless non-loopback process
serve unauthenticated inference. Stop if the HTML handoff would apply to
`/v1` or to a credentialed API route. Stop if the only way to preserve a
legacy install is to keep generating a dead key on the fresh path.

## 15. Closure evidence required

Commands and results. Tests named above and the legacy-key negative.
Before/after description of onboard's writes. Confirmation that no
migration, dependency, or auth-mode change landed. Registry row moved
only in the closure commit.

## 16. Handoff notes

The personal token is already printed by `print_one_time_secret`. Do not
add a second disclosure path. The sign-in transport gate in
`rust/src/server/auth.rs` still refuses a password form over remote
plaintext HTTP. The handoff page may link to `/login`; it must not embed
a password form on an unsafe transport. Serial tests only.

## 1. Purpose and ownership boundary

Close the solo-install and small-team gaps found in the 2026-11-10 audit
without reopening the closed on-prem user-access roadmap. That roadmap's
M001–M024 records stay immutable.

This roadmap owns the member-visible projection of identity, budgets, and
navigation, the fresh-install credential handoff, and, after ADR-0010 is
accepted, personal upstream custody.

| Concern | Owner |
|---|---|
| Onboarding credential handoff | `rust/src/runtime.rs`, `rust/src/operations/config_mutation.rs` |
| Browser sign-in and route gate | `rust/src/server/auth.rs`, `rust/src/server/middleware.rs` |
| Usage and limit projection | `rust/src/server/dashboard/admin.rs`, `rust/src/server/dashboard/render/admin.rs`, `rust/src/server/health.rs`, `rust/src/user_budget.rs`, `rust/src/instance_budget.rs` |
| Navigation chrome | `rust/src/server/dashboard/render/layout.rs` |
| Personal upstream grant, binding, and eligibility | `rust/src/identity.rs` or a new sibling module under `rust/src/`, `rust/src/routing/eligibility.rs`, `rust/src/accounts/registry.rs`, `rust/src/config.rs`, `rust/src/config_reload_policy.rs` |
| Secret file | `rust/src/operations/paths.rs` and the config-adjacent `.env` writer already used for operator keys |

`rust/src/coordinator/` keeps publication and settlement. `rust/src/db/`
keeps the single writer. Provider transport and the bundled profile
contract stay where they are. This roadmap does not add a provider.

## 2. Work classification

### Invariants

- One SQLite writer, WAL/NORMAL, and generation publication stay in place.
- Credentials stay out of SQLite, logs, diagnostics, and reload diffs.
- Day and month usage buckets are never added together into one displayed total.
- A bound upstream account is never selectable by a different principal.
- Model policy, user budget, and provider health/quota still run. A personal
  account cannot pin selection or skip them.

### Capabilities

- A fresh `eggpool onboard` leaves the operator with one working personal
  token and a browser path to `/login`.
- A member sees their own limits, current-window usage, and remaining
  allowance against their own rules, plus the configured instance ceilings
  without anyone else's consumption.
- A member's pages link only to member destinations.
- An administrator can read each user's current profile, budgets, and
  credential labels from the users page.
- After ADR-0010 is accepted, a granted member can add a bundled-provider
  upstream account that only they can use, and an administrator can allow
  or deny that ability for the instance or for one user.

### Infrastructure

- Secret-free binding rows and a generation-scoped eligibility snapshot.
- File transaction around TOML and `.env` that fails closed.

### Polish

- USD display beside stored microdollars.
- Users-page actions grouped so the current assignment is visible.

## 3. Non-goals

- Reopening or rewriting on-prem user-access M001–M024.
- A second administrator, public signup, SSO, or an organization id.
- Amazon Bedrock or any other provider that is not already in the bundled
  profile asset.
- Member-supplied base URLs, proxies, headers, or weights.
- Preferring a personal account over the normal load-based choice among
  accounts that member is allowed to use.
- Showing one member another member's usage, or the remaining headroom of
  the shared instance ceiling.
- Editing v1–v65 migrations. v65 tool-grant tables stay unused by this work.

## 4. Current state

Baseline `9da5e2d383c73035850c37f8125c145b8b7ff9ff`.

Fresh onboard in `rust/src/runtime.rs` generates `[server].api_key` and
then bootstraps the administrator in the same run. Bootstrap sets
`admin_initialized`, after which `legacy_server_key_allowed` rejects that
key. The operator's working credential is the one-time personal token.
`rust/config.example.toml` still says the server key generated by onboard
guards inference.

An unauthenticated dashboard GET, once identity is initialized, receives
JSON `{"detail":"Sign in required"}` from `rust/src/server/middleware.rs`.
The sign-in form is `GET /login`.

`user_budget_usage` stores one day row and one month row per settled
request. The admin usage query sums those rows by user and model. The
member table omits the window kind. `/api/user-budget` returns the member's
rules and usage. Instance rules and instance usage are added only for an
administrator. `docs/model-limits.md` says instance ceilings are
admin-visible only.

`dashboard_standalone_page` renders the full operator navigation for member
pages. The users table shows role and state, then stacks every mutation in
one cell, without the current profile, overrides, budget rules, or
credential labels.

`AccountConfig` and `AccountIdentity` have no owner. Routing eligibility
does not receive a user id. ADR-0010 is now accepted and is the authority for the granted path.

## 5. Target architecture

Solo and team installs share one process. The fresh path creates the
administrator and a personal client token and does not also create a server
key that the same command retires. Browser navigation to a protected HTML
page offers `/login`. Machine clients of `/v1` and `/api` keep JSON.

Usage projections group by window. A member sees their rules, settled rows
labeled day or month, remaining allowance on their own current windows, and
the configured instance ceiling values. Instance usage totals stay on the
admin response.

Member HTML uses a member navigation set. The users page shows the current
assignment and groups mutations under it.

Personal upstreams, after acceptance, are shared accounts plus an optional
binding. The secret stays in `.env`. Selection subtracts accounts the
principal does not own before scoring.

## 6. Dependency graph

- M001, M002, and M003 have no hard dependencies. They may proceed in
  parallel. Soft: M003 does not redesign the usage tables owned by M002.
- M004 has a hard dependency on acceptance of ADR-0010, including the
  canonical sentence amendments that acceptance names. Interface: the
  binding row and eligibility snapshot are the contract M005 consumes.
- M005 has a hard dependency on M004. It does not choose a second custody
  design.

## 7. Milestones

### Milestone 1 — Solo sign-in and onboarding credential

Class: capability

Objective: A fresh onboard yields one usable personal token and a browser
path to sign in, and it does not present a server key that the same run
retires.

Dependencies: none.

Deliverable boundary: `rust/src/runtime.rs`, the unauthenticated HTML
response in `rust/src/server/middleware.rs` and `rust/src/server/auth.rs`,
and the operator sentences that describe the fresh-install key.

User or operator value: Solo setup matches the credential that actually
works.

Exit conditions: A new database onboard writes no `[server].api_key`. An
existing key is left in place and the command says inference uses the
personal token. Unauthenticated HTML GET of a dashboard or account page
in `admin_initialized` or `managed` offers `/login` and is `no-store`.
`/v1` and `/api` remain JSON 401. Legacy `legacy_unmigrated` behavior is
unchanged.

Deferred work: Personal upstream keys.

### Milestone 2 — Usage windows and member limits

Class: capability

Objective: Displayed usage does not add a day bucket to its month bucket,
and a member can see their own limits and remaining allowance.

Dependencies: none.

Deliverable boundary: usage queries, member and admin renderers, and
`GET /api/user-budget`. No schema change.

User or operator value: A member can tell what they have spent and what
remains. An administrator sees per-user totals that match one window.

Exit conditions: Admin totals are computed inside one window kind. Member
rows show the window kind. Remaining allowance for the current UTC day and
month subtracts settled usage and active holds for that member's own rules.
Instance ceiling configuration is visible to the member. Instance usage and
other users' rows are not. `docs/model-limits.md` matches that split.

Deferred work: Editing another user's budget from a redesigned roster. That
is M003's presentation of rules M002 does not need to move.

### Milestone 3 — Member navigation and admin roster

Class: polish

Objective: A signed-in member is offered only member destinations, and the
users page shows the assignment those destinations depend on.

Dependencies: soft on M002, so the usage page's numbers stay M002's.

Deliverable boundary: navigation markup and the users/profile renderers and
their tests. No new authority.

User or operator value: A member stops landing on administrator 403 pages
from the navigation. An administrator can see the current profile, budget
rules, overrides, and credential labels.

Exit conditions: Member HTML from `/my-account`, `/my-account/models`, and
`/usage` does not link to operator routes. Operator URLs still return the
member refusal. The users row shows the assigned profile, or that the
member is unassigned and therefore denied. Saved microdollar limits also
show USD. The stored unit remains microdollars.

Deferred work: Personal upstream grant controls. Those wait for M005.

### Milestone 4 — Personal upstream custody and routing

Class: infrastructure

Objective: Provide a secret-free binding and a CLI consumer so a personal
upstream account is eligible only for its owner.

Dependencies: hard on ADR-0010 acceptance and the canonical amendments that
acceptance requires.

Deliverable boundary: one new migration, the binding service, `.env` and
TOML transaction, generation snapshot, eligibility filter, and
`eggpool users upstream` subcommands. No browser form.

User or operator value: A headless administrator can attach an individual
bundled-provider key to one user and can set the self-service grant. The
running server routes only that user to it.

Exit conditions: The CLI contract in the implementation plan passes,
including failed-reload restoration and cross-user denial. The secret is
absent from the database and from diagnostics. Default grant is `deny`, so
an unconfigured instance behaves as it does today. This milestone is not a
completed member-facing capability; M005 is that consumer.

Deferred work: The browser form and the users-page grant controls.

### Milestone 5 — Personal upstream browser grant

Class: capability

Objective: Let a granted member add and remove their own bundled-provider
account in the browser, and let an administrator set the grant there.

Dependencies: hard on M004.

Deliverable boundary: member and admin HTML forms, route-role entries, and
browser tests. Custody and eligibility stay in M004.

User or operator value: The small-team path no longer requires a shell to
add a personal OpenCode Go key, and the administrator can withdraw that
ability without editing TOML by hand.

Exit conditions: A denied member sees no secret field and receives a
refusal. A granted member adds an account and can call through it. Another
member cannot. Personal API tokens cannot call the mutation. The
administrator can set instance and per-user grants and can remove an
account.

Deferred work: New providers, custom endpoints, and account preference.

## 8. Cross-cutting requirements

Storage: M001–M003 and M005 add no tables. M004 appends the next migration
after v65 and a checksum. Bindings store ids and state only.

Protocol: `/api/user-budget` may add fields. It does not remove or rename
`rules` or `usage`. Inference request bodies are unchanged.

Security: M001 does not open a new unauthenticated inference path. M004
rejects the secret from argv, logs, and SQLite. Self-service mutations
require a browser session.

Concurrency: usage reads are consistent with the single writer. Binding
publication is generation-scoped. In-flight requests do not reselect.

Observability: new audit actions record actor, action, and account name.
They do not record the secret.

Performance: eligibility adds a membership test on the existing candidate
set. No new routing lock and no second database worker.

Docs: operator docs change in the milestone that changes the behavior.
`AGENTS.md` does not gain a copy of this roadmap.

## 9. Verification strategy

Rust tests stay serial. Focused targets:

- M001: `rust/src/runtime.rs` onboard tests, `rust/tests/on_prem_sessions.rs`, middleware auth tests.
- M002: `rust/tests/on_prem_budgets.rs`, `rust/tests/on_prem_global_budgets.rs`, `rust/src/server/dashboard/tests.rs`.
- M003: `rust/tests/on_prem_admin_ui.rs`, `rust/src/server/dashboard/tests.rs`.
- M004: `rust/tests/on_prem_identity.rs`, routing eligibility tests under `rust/tests/`, migration coverage in the database test target, `--no-default-features` check and clippy.
- M005: `rust/tests/on_prem_admin_ui.rs` and session CSRF tests.

Closure of any milestone that changes `README.md` or `docs/` runs
`uv run python scripts/validate_release_docs.py`. The full serial workspace
suite is closure evidence, not a substitute for the focused tests.

## 10. Risks and decision points

ADR-0010 is accepted, with the named canonical amendments. M001–M005 are closed. Their records are `plans/closure/on-prem-member-access/001-status.md` through `005-status.md`. The serial suite, the no-default check and clippy, and the locked release build are recorded there.

Showing instance ceiling values to members reveals the cap and does not
reveal other people's consumption. Showing remaining shared headroom would.
M002 keeps remaining shared headroom admin-only.

A personal account that loses its binding before its config stanza is
removed would become shared. M004's state machine forbids that transition.

## 11. Completion definition

M001–M003 are closed on their exit conditions. M004 and M005 are closed
only after ADR-0010 is accepted and their own closure records exist. The
roadmap then closes. Solo onboard, member usage, member navigation, and
grant-controlled personal upstreams are the four observable results. No
Bedrock provider is implied.
